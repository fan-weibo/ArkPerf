# 冷启动基线对比

判定「启动变快了」**必须走先量基线、改完再比两步**。两次随意测量的绝对耗时相减
不构成结论：模拟器常驻时环境整体会漂移，两次会话的数字根本不可比。

## 1. 先在**未改动**的代码上量基线

```
mcp_cold_start_cold_start_measure(bundle_name="<包名>")
```

- 保持 `anchor=true`（默认）。开启后每一轮都会紧接着再测一次系统设置应用，
  记录「目标耗时 / 锚点耗时」的比值。**环境整体漂移时，比值不变而绝对值会变**，
  所以模拟器上这是唯一可靠的抵消手段。
- `runs` 默认 10。判定「显著」靠的就是采样量，不要为省时间降到 3 以下。
- **不要用 `quick=true` 来做对比**：它会把采样降到 5 轮，**并且把 `anchor` 一起关掉**
  （`anchor = None`），归一化结果直接拿不到。快速模式只能用来先看一眼有没有明显问题。
- 返回里既有绝对耗时也有锚点归一化结果。**有锚点时以归一化结果为主结论。**

## 2. 改代码，然后在同一环境下重测并对比

```
mcp_cold_start_cold_start_compare(bundle_name="<包名>")
```

两次调用的 `anchor` 必须一致。以下两句出现时**不要下结论**：

- 「两次会话的锚点应用不一致，归一化结果不可比」——先统一锚点设置再重测。
- 「锚点自身耗时变化超过 10%，环境已漂移」——按工具提示以归一化结果为准；
  若归一化结果也拿不到，说明这一轮环境不可用，重跑。

## 3. 结论怎么写

- 只引用工具给出的判定（显著改善 / 显著退步 / 无显著差异）与它返回的数字，
  **不要自己拿两次的均值算百分比**。
- 出现「建议增加采样次数」之类的提示时，先照做再下结论。
- 拿不到数据就说拿不到。用一次测量的数字声称优化有效，是最容易被追问倒的一种错。
