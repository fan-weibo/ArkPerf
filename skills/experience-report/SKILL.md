# 全量体验分析 + 报告归档

单项工具回答的是「这一项有没有问题」；这个技能回答的是
「整体怎么样，并且给我一份能拿去对比的东西」。

## 何时用，何时别用

- **用**：用户要整体结论、要一份报告、要做优化前后归档、问题还没定位到具体维度。
- **别用**：用户已经明确问某一项（例如「内存有没有泄漏」）。全量分析会驱动模拟器
  跑完整采集，耗时数分钟，用来回答一个单点问题不划算——那个场景用对应的单项技能。

## 步骤

1. 先问工具支持哪些指标，不要凭印象列清单：

   ```
   mcp_experience_list_indicators()
   ```

   它返回本 Agent 支持的体验指标与对应的可识别问题。**结论里出现的指标名
   必须来自这里**，不要写出工具根本测不到的东西。

2. 选一种跑法：

   ```
   # 只要结论，不落盘
   mcp_experience_experience_analysis(bundle_name="<包名>")

   # 要归档（推荐：优化前后各跑一次，用 tag 区分）
   mcp_experience_save_experience_report(bundle_name="<包名>", out_dir="reports", tag="baseline")
   ```

   常用参数：`ability_name`（只关心某个 Ability 时指定）、`modules`（只分析指定模块）、
   `scene`（指定场景）、`quick`（见下面的坑）、`tag`（归档标记）。

## `quick` 有一个必须先知道的坑

`quick=true` **不只是采样变少，它会把冷启动的锚点归一化一起关掉**：

| | 标准（quick=false） | 快速（quick=true） |
|---|---|---|
| 冷启动轮数 | 10 | 5 |
| 内存压力周期 | 5 | 3 |
| CPU 采样 | 3 | 2 |
| 卡顿轮数 | 5 | 3 |
| **锚点归一化** | **开启** | **关闭** |

锚点是唯一能抵消模拟器环境整体漂移的手段。**做优化前后对比时绝对不要用 `quick`**，
否则两次报告里的绝对耗时不可比——你会把环境漂移报成优化效果。快速模式只适合
「先看一眼有没有明显问题」，不适合出结论。

## 优化前后对比的纪律

两次之间只允许代码变，以下参数必须完全一致：`bundle_name`、`modules`、`quick`、`scene`。

`tag` 用 `baseline` / `optimized` 这类固定词，不要用时间戳——时间戳会让
「哪份是基线」变成要靠猜的事。

报告默认落在**工作区下的 `reports/`**（`out_dir="reports"`，目录会自动创建），
文件名形如 `report-20261005-051307-baseline.md`。所以两次对比报告会并排躺在
同一个 `reports/` 里，一眼能看出先后。要归档到别处再显式传绝对路径。

## 耗时与预期

一次全量分析要驱动模拟器跑完整采集，**耗时是分钟级的**（工具超时按 360 秒配置）。
不要因为它迟迟不返回就判定卡死、也不要中途放弃——那会浪费掉一整次测量。

## 报结论时

- 引用的数字必须来自工具返回的报告；不要拿不同批次、不同参数的两份报告混着算。
- 归档产出 Markdown + JSON 两份：Markdown 给人看，JSON 给后续对比用。
- 哪一项没测成就说没测成。**「没发现问题」和「没测到」是两件事**，
  混为一谈会让用户误以为优化有效。
