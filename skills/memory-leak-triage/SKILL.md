# 内存泄漏判定

「内存涨了」不等于「泄漏」。这是本任务里最容易出错的一步，因为**缓存填充**
和**真泄漏**在单次快照上长得一模一样。

## 先理解判据，否则会误判

工具看的是**每个压力周期的回落点是否逐次抬升**，据此分三种形态：

| 形态 | 回落点 | 含义 |
|---|---|---|
| 锯齿（sawtooth） | 稳定 | 正常，回收正常 |
| 阶梯（staircase） | 逐次抬升 | 疑似泄漏 |
| **有界增长（capped）** | 前段抬升、**后段饱和** | 缓存填满，**不是持续泄漏** |

第三种是关键：一次性把数据读进缓存、填满后不再增长，全程速率可能远超阈值，
但后段斜率会归零。**不区分它就会把正常缓存判成泄漏**，进而去改一段本来没问题的代码。

速率阈值（工具内部判定，引用它返回的结论即可，不要自己算）：

- < 0.5 MB/min 稳定
- < 2 MB/min 缓慢增长，建议关注
- ≥ 2 MB/min 疑似泄漏
- 上升点占比需 ≥ 0.7 才算「持续增长」，所以偶发波动不会被判成泄漏
- 少于 3 个有效周期**无法判趋势**——那时工具会给出「周期数不足」，照它说的加重测

## 步骤

1. 先建立量级认知，看当前水位：

   ```
   mcp_memory_memory_snapshot(bundle_name="<包名>")
   ```

   得到 PSS 总量 / ArkTS 堆 / Native 堆三个维度。

2. 跑多轮压力循环做判定：

   ```
   mcp_memory_memory_leak_check(bundle_name="<包名>", cycles=5, workload=true, gc=true)
   ```

   - `cycles` 别降到 3 以下：少于 3 个周期判不出趋势，只能得到「周期数不足」。
   - `gc=true`（默认）表示在周期之间触发回收。关掉它测到的是「没回收」而不是「泄漏不了」，
     汇报时必须说明这一项。
   - 返回值里带 `gc_supported` / `gc_enabled`：设备不支持 GC 时它会如实标记，
     这种情况下不能把涨的那部分直接算成泄漏。

3. 想看增长曲线而不是只看结论时：

   ```
   mcp_memory_memory_trend(bundle_name="<包名>", duration=10, interval=1.0)
   ```

   ⚠️ **这个工具不触发 GC，它的曲线不能用来判泄漏。** 堆在两次 GC 之间上涨是
   垃圾回收器的正常工作方式，所以 `memory_trend` 单调上升只说明"产生了垃圾还没回收"。
   见过把它 3822→4170 当成"疑似泄漏"的误报——正确做法是：这条曲线只用于观察过程，
   **结论一律以 `memory_leak_check` 的回落点为准**。
   
   如果两个数据看起来打架（曲线在涨、判定却是锯齿），那不是工具坏了，
   是它们在测两个不同的量（未回收的占用 vs 回收后仍持有的内存）。
   此时以回落点为准，并在结论里把这一点解释清楚。

## 报结论时

- **必须区分 PSS / ArkTS 堆 / Native 堆**，工具是按维度分别判定的（例如
  `judge_staircase(..., "PSS")` 与 `judge_staircase(..., "Native 堆")`）。
  三者涨的位置不同，根因方向完全不同。只说「内存涨了」等于没给结论。
- 引用工具给出的形态标签与速率，不要从序列里自己算斜率。
- 判定为泄漏时，结论要能复现：说明用了多少周期、每周期做了什么压力、GC 是否开启。
